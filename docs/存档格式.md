# 存档格式

> RPG Maker VX Ace（RGSS301 / Ruby 1.9 Marshal 4.8）
> 本文所有结论都是**实测**得到的（脚本见 `tools/`）。

## 0. ⚠ 先看这个：两个游戏版本的存档格式**完全不同**

本仓库（`beta` 分支）适配**内测版 V2.201**；`main` 分支适配**尝鲜版 v0.x**。
两者**不能互换工具**，架构上也不共用同一套加解密（见下表）。

|环节 | 尝鲜版（`main` 分支） | **内测版 V2.201（本分支）** |
| ------------------ | --------------------- | ------------------------------------------ |
| 存档分组| 8 字节自定义 ECB | **16 字节 AES-128-ECB** |
| 存档压缩层         | **无**（直接是 marshal 流） | **有**（`Zlib::Deflate` / `Inflate`） |
| 存档密钥           | `tiyan_version`（6 字节） | **`153ad4v3fbdgbgd`**，15 字符**零补齐**到 16 字节 |
| `Data\*.rvdata2`   | 同一套 8 字节 ECB，密钥 `761205` | **按文件名派生的 RC4**（见 §2.2） |
| 加解密靠谁         | `System\main.dll` 导出 + 32 位宿主 | **纯 Python**（`src/save_v201.py` / `src/data_v201.py`） |

> **V2.201 的 `main.dll` 加壳后导不出加解密函数**（实测宿主报 `[ERR] … = 126`），
> 所以内测版这条线**完全不走 dll**，两套算法都是纯 Python 复刻。

**V2.201 存档格式**（实测往返通过）：

```
写：marshal(header) + marshal(contents) → Zlib::Deflate → 零填充到 16 → AES-128-ECB → save.rvdata2
读：AES-128-ECB 解密 → data[0]=='x' 则 Inflate → Marshal.load ×2
```

⚠ 15 字符口令**必须零补齐**成 16 字节当 AES 密钥（`153ad4v3fbdgbgd` + 一个 `\0`）——
直接拿 15 字节去用会报 `ERR_CRYPTO_INVALID_KEYLEN`，症状是「密钥明明对了却解不开」。

下面 §1 / §2.1 是**尝鲜版**的原始记录（保留作对照），§2.2 起是**内测版 V2.201** 的实测结论。

---

## 1. 文件在哪儿（两版通用）

| 文件                                     | 说明                                                                                        |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| `<游戏根>\save.rvdata2`                | 手动存档                                                                                    |
| `<游戏根>\AutoSave\save00..29.rvdata2` | 自动存档（`Config.ini` 里 `auto_save_max=100`）                                         |
| `<游戏根>\Data\*.rvdata2`              | 数据库（System / Actors / Items / MapNNN …）                                               |
| `<游戏根>\Data\Scripts.rvdata2`        | 游戏脚本本体（被加密藏起来了）                                                              |
| `<游戏根>\Data\main.rvdata2`           | 脚本入口。**两版差别很大**：尝鲜版只有一句 `Win32API.new('System/main','qqeat',…).call`；V2.201 是 4891 条的骨架，只有 id=2546（662B）是真引导段 |
| `<游戏根>\System\Game.md5`             | 被加密的完整性清单（只含 Game.exe 和 main.dll 的 md5）                                      |
| `<游戏根>\was.info`                    | **明文** Marshal，与存档逻辑无关                                                              |

## 2. 加密：谁在加、用什么密钥

### 2.1 尝鲜版（`main` 分支，本分支不适用）

加密由 `System\main.dll` 的导出完成：

```
decryption_file(输入路径, 输出路径, 密钥)  -> 0/1     (stdcall；三个参数都是 UTF-8 char*)
encryption_file(输入路径, 输出路径, 密钥)  -> 0/1
```

**第三个参数就是密钥字符串。** 密钥不对时 DLL 不报错，而是**写出 0 字节的空文件** ——
所以"输出非空 = 命中"这个判据非常干净（爆破时唯一的信号就是它）。

逆向出来的三个密钥：

| 密钥                | 用途                                           |
| ------------------- | ---------------------------------------------- |
| `761205`          | `Data\*.rvdata2` 数据库、`System\Game.md5` |
| `imoutogadaisuki` | `Data\Scripts.rvdata2`（脚本本体）           |
| `tiyan_version`   | 存档`save.rvdata2` / `AutoSave\*.rvdata2`  |

* `761205` / `imoutogadaisuki` 藏在 main.dll 解壳镜像 RVA `0x118850` 附近的常量区；
* `tiyan_version` 写在游戏脚本的 `Config::File::SAVE_FILE_PASSWORD` 里。

密文形态（任意明文实测）：

* 密文长度一定是 8 的倍数；
* 同一明文的相同 8 字节块 → 相同密文（ECB，无随机量、无 IV）；
* 密钥错了输出的"垃圾"也一样是 8 字节一组。

### 2.2 内测版 V2.201（本分支，2026-10-02 实测）

**存档**：见 §0 的 AES-128-ECB + Zlib 格式。口令来自游戏脚本
`Config::File::SAVE_FILE_PASSWORD`。实现见 `src/save_v201.py`（纯 Python，零外部依赖）。

**数据表 `Data\*.rvdata2`**：换成了**按文件名派生的 RC4**：

```ruby
pwd = '9KQ1L0PWRESZV7HM' + Zlib.crc32(File.basename(name)).to_s(36)[0..12]
密钥 = pwd[-16..-1]        # ⚠ 是**后** 16 个字符
数据 = Base64.read(文件)   # IO.binread 后直接 RC4，没有 Base64 层
```

实测 `Data` 下 **403 / 403** 个表全部解出 `\x04\x08` Marshal 头。实现见 `src/data_v201.py`。

⚠ **两个必须记住的坑**（我第一次就踩了）：

1. **密钥取`[-16:]`（后 16），不是 `[:16]`（前 16）**——
   前 16 恒等于 `'9KQ1L0PWRESZV7HM'` 这段常量、**对所有文件都一样**，
   于是看起来算对了、实际谁也解不开；
2. `crc32` 取的是**带扩展名**的文件名（`Actors.rvdata2`，不是 `Actors`）。

**两个例外，不要用 RC4 去解**：

* `Data\main.rvdata2` —— 本身是明文脚本骨架；
* `Data\Scripts.rvdata2` —— RC4 也解不开，内容是空壳脚本档。


## 3. 解密后的明文：两个 Marshal 对象拼在一起

游戏是这样写档的（脚本里 `DataManager.save_data`）：

```ruby
Marshal.dump(make_save_header, file)     # { :temp => nil }
v = make_save_contents                   # 一个 Hash
Marshal.dump(v, file)
```

所以明文 = `04 08 {...}` + `04 08 {...}`；**每个顶层对象各自带 04 08 头，
各自从 0 开始算对象编号/符号编号**，解析时必须每个对象重置链接表。

`make_save_contents` 的 11 个键（顺序固定）：

```
:system  :timer  :message  :switches  :variables
:self_switches  :actors  :party  :troop  :map  :player
```

实测 `save.rvdata2`：密文 310448 字节 → 明文 310437 字节 → 解析结束位置正好 310437。
（另一台/另一次存档实测 312404 字节，同构。）

### 各分区的类与关键字段

| 分区                   | 类                             | 有用的字段                                                                                                                                                                    |
| ---------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `:system`            | `Game_System`                | `@seeds`（Hash；`[:shield]` 是防作弊种子）、`@save_count`、`@cheated`、`@keyword`、`@config`（含**机器码**，见 §6）、`@security`（五类记账：金钱/物品/变量/人气/贡献，见 §8） |
| `:switches`          | `Game_Switches`              | `@data` = Array（下标 = 开关编号）                                                                                                                                          |
| `:variables`         | `Game_Variables`             | `@data` = Array（下标 = 变量编号）                                                                                                                                          |
| `:actors`            | `Game_Actors`                | `@data` = Array（下标 = 角色 id，元素是 `Game_Actor`，带 `@babies` 召唤兽）                                                                                             |
| `:party`             | `Game_Party`                 | `@gold`（`Lock` 包装，界面叫“金钱”）、`@actors`（角色 id 数组）、`@items`/`@weapons`/`@armors`（Hash：格子号 => [对象, 数量]）、`@steps`、`@warehouse_page` |
| `:map` / `:player` | `Game_Map` / `Game_Player` | 地图 id、坐标等                                                                                                                                                               |

## 4. 防作弊：`Lock`

关键数值（金钱等）不是裸整数，而是 `Lock` 对象：

```ruby
class Lock
  def initialize(v)
    @value = v
    @master = get_encryption(@value)
  end
  def seed; $game_system.seeds[:shield]; end
  def get_encryption(v); v * 91 + 45 + seed / 800; end   # Ruby 里 / 是整除
  def show
    if get_encryption(@value) != @master
      msgbox '游戏异常！'
      exit                        # ← 直接改 @value 就会踩这里
    end
    return @value
  end
  def +(other); self.class.new(show + other); end         # 四则运算都会重建 Lock
end
```

所以"改钱"的正确做法是：

```
@value  := 新值
@master := 新值 * 91 + 45 + $game_system.seeds[:shield] / 800     # 整除
```

`src/save.py` 的 `set_gold()` 会自动同步；`repair_locks()` 会扫全档修所有 Lock。

> 本机实测：`seeds[:shield] = 237599985163622727515788549406877775289`，
> 原档 `@gold @value = 1164` → `@master = 296999981454528409394735686758703188`，
> 用上面的公式正好算得出来 —— 说明公式复刻无误（`tests/test_save_layer.py` 会验证）。
>
> 另外注意 `@master` 是 **Bignum**（大整数），写回时要按 `l` 类型编码。

## 5. 背包：4 页×20 格

`Game_Party` 里三个 Hash：`@items`（道具）/ `@weapons`（武器）/ `@armors`（防具），
**key 是“格子号”，不是物品 id**：

```
格子号 = 页号 * 20 + 格内序号          页 0..3，格 0..19（对应游戏道具菜单的 4 页）
@items[格子号] = [ 物品对象, 数量 ]     物品对象是从 Data\Items.rvdata2 复制的
                                      （@id 才是真正的物品 id）
```

* 空格子：key 不存在，或 value 是 `nil`。
  清空格子用“置 nil”而**不是删 key**：不改变对象个数 → 不会踩 `@N` 编号错位的坑。
* 加物品：从 `Data\<kind>.rvdata2` 里克隆模板对象。
  模板只有 19 个 ivar，存档里的实物还多了游戏自己加的 5 个：
  `@result_note` / `@attr` / `@update` / `@new` / `@transaction_code`，
  新建时要一并补上（`@transaction_code` 是随机大整数）。
* 仓库另有页号：`@warehouse_page`（内测版 V2.201 是 0..12，尝鲜版 0..3）。
* 上限：`Config::Game::MAX_GOLD`（内测版 **9,999,999,999**、尝鲜版 30,000,000）、
  物品单格上限 99（工具里放宽到 99*99）。

## 6. 物品的“运行时内容”：`@attr`（脚本里叫 `item.data`）

物品不只存在 `Data\\Items.rvdata2` 里的那些字段：游戏发给你的时候会**现抽内容**
写进物件的 `@attr`。孵化蛋就是典型：

```ruby
class Game_Party
def 孵化蛋(item)
  i = item.id - 110
  item.data = { type: :baby_egg, data: { id: [
      rand(21..23, 25..63), rand(64..95, 127..134), rand(96..126),
      BabyManager.select_babys{|b| b.read_note('data').in?(:神兽资质, :神兽资质2)}.sample,
    ][i] } }
end;end
```

存档里就是这个形状（符号键）：

```
@attr = {:data => {:type => :baby_egg, :data => {:id => 57}}}
@result_note = {:icon => "蛋-初级"}
@update = false            @new = false
@transaction_code = <128 位随机大整数>
```

⚠ **`@attr` 是空的话一用就报错**：使用时会 `d = item.data[:data]; d[:id]`，
空 Hash 让 `item.data[:data]` 返回 nil，于是
`NoMethodError: undefined method '[]' for nil:NilClass`。
所以从模板“凭空造”这类物品时必须把内容一起造出来（或直接从存档里克隆同款）。

已知家族（脚本 `Game_Party#名字(item)`，`src\itemattr.py` 把它们照抄成了 Python）。
⚠ **`type` 是中文符号**（游戏按 `case item.data[:type]` 分发，写英文名它认不出）；
`data` 那一列的 **结构** 也照游戏写的那份 —— 多数家族是 `{"data": {...}}`，
`礼盒` 是 `{"list": [...]}`（**没有 `data` 层**）：

工具侧：

* 加这类物品时优先**克隆存档里同款**，没有才按上表现生成；
* 「背包 / 物品」页的格子列表有 **“内容”列**（`蛋→狐狸精(37)`），缺内容一眼可见；
* 「背包体检」会把 `@attr` 空的列出来，「一键修复」直接补；
  「重抽管理」可以按规则重新抽，或**按这件东西的家族**挑具体内容
  （`itemattr.payload_spec()` 报可挑字段，`game.set_payload(..., over=…)` 落地）；
  字段 `kind` 是 `"int"/"num"` 且带 `rng`（或随别的字段走的 `rng_by_type`，元宵的
  「数值」就是跟着「涨哪项资质」）时，界面**默认填区间上限**（成长 0.02），
  输入框清空＝不看这一项、交回游戏规则随机；
* 已实测：`tools\\probe_payload_now.py --fix` 在副本上修复后再保存重开，
  `@attr` 依旧在，游戏里能正常显示【诞生对象】。

## 7. 机器码（存档绑定）

游戏用 `main.dll` 的 `get_hard_disk_character()` 取本机机器码（一串 9 位数字）：

```ruby
GET_HARD_DISK_CHARACTER = Win32API.new(dll, 'get_hard_disk_character', 'v', 'p')
# 取不到时返回 '0'（游戏提示“发生意外错误, 无法开始游戏！”）
# 存档初始化时：
config[:hard_disk_code] = [GET_HARD_DISK_CHARACTER.call]      # 数组
# 启动时比对：
code = GET_HARD_DISK_CHARACTER.call
if !$game_system.config[:hard_disk_code].include?(code)
  msgbox "存档异常！#{code}"
  exit
end
```

所以存档是**绑机器**的（可以同时绑多台）。本工具：

* ⚠ **两个版本读法不同**：
  * **内测版 V2.201（本分支）**：用**纯 Python** 实现（`src/machine_id_v201.py`）——
    `CreateFileA("\\\\.\\PhysicalDrive0", 0)` → `DeviceIoControl(0x2D1400)`
    → CRC32(整个 1024 字节输出缓冲) → 十进制。**不碰 main.dll、不需要管理员权限**。
    （V2.201 的 main.dll 加壳后导不出 `get_hard_disk_character`，走 dll 必然失败。）
  * 尝鲜版（`main` 分支）：宿主 `XJCodec32.exe machine <main.dll>` 调那个导出。
    本分支也保留了这条路作兜底（纯 Python 取不到时才走）。
* 算法本身**两个版本一致**（川 2026-10-02 确认），所以纯 Python 版对两版都适用。
* ⚠ CRC32 的两个坑：① 参与计算的是**整个 1024 字节缓冲**（含尾部未写满的 0），
  不是某个字段；② 参数就是 `zlib.crc32`（`init=0xFFFFFFFF`）——
  反汇编里读到 `0x7FFFFFFF`，但**实测 `0xFFFFFFFF` 才命中**，以实测为准。
* 本机实测值 = `630693299`。若存档里记的是别的值（如 `1079307699`），
  说明该档是配合机器码伪装器/离线替身产生的，**本机真实码与之不同是正常的**。
* 其余操作：`GameEditor.machine_ids()` 读存档里的数组，`add_machine_id()` 追加、
  `set_machine_ids()` 整组替换；界面在「概览 / 快捷修改」的**机器码面板**。
* ⚠ **保存 / 自动修复都不碰机器码**：`anti_cheat_report()` 里那一项固定
  `bad=False`（只提示「本机码不在档 ⇒ 游戏在本机读档会弹『存档异常』」），
  `fix_anti_cheat()` 不再追加本机码 —— 否则把码换成别人的（伪装）之后一保存
  就被塞回本机真实码，替换白做。要改只能手动点面板上的按钮。

存档里的位置：

```
:system → @config（Hash，键都是符号）
    hard_disk_code: ["1079307699"]        ← 机器码数组（V2.201 实测是**单元素**）
    network_synchronous_code: 0
    send_temp: 0
    shortcut_skill / show_mp_bar / dead_battler_command
```

## 7. 召唤兽：`Game_Baby` / `Game_Baby_Attr`

每个角色（`Game_Actor`）有一个 `@babies`（数组），元素是 `Game_Baby`；
资质与五维放在中文 ivar 的 `Game_Baby_Attr` 里（和角色的 `Game_Actor_Attr` 一个路子）。

| 字段                        | 含义                                | 上限  |
| --------------------------- | ----------------------------------- | ----- |
| `@level`                  | 等级                                | 65    |
| `@hp` / `@mp` / `@tp` | 气血 / 魔法 / 灵力                  | —    |
| `@exp`                    | 经验                                | —    |
| `@life`                   | 寿命                                | 12000 |
| `@loyalty`                | 忠诚（<60 不能参战）                | 100   |
| `@growth`                 | 成长                                | —    |
| `@attr`                   | `Game_Baby_Attr`：六项资质 + 五维 + 五行 | —    |

召唤兽的五行是 `@attr.@five`（Marshal **字符串**，金 / 木 / 水 / 火 / 土，出生时随机，
炼妖的相生相克看它 —— `Window_Demon#five_calc`）；写别的值游戏取不到，工具会挡下。

预设按钮（一键满级/经验拉满/全员状态拉满/寿命满/资质+100/资质+500/成长+0.1/五维+10）
都是直接改这些字段。
「全员状态拉满」一次改**所有角色**的**所有召唤兽**（气血/魔法/愤怒回满 + 忠诚拉满，
合了老的「回满气血/魔法」与「全员忠诚满」）；忠诚只在一处起作用 ——
`>= 60` 才能参战（`Config::Baby::ALLOW_LOYALTY`），没有任何属性加成，`$jiance` 也不查它。

## 8. 物品计数校验：`Change`（AES）

`:system` 下的 `@security[:items]` 是一个 Hash：**物品 id => `Change` 对象**。

```ruby
class Change
  def initialize(code)
    @code = code                     # 一段 Ruby 片段，当场算出“应该是多少”
    @value = @code.split('').map{|c| encrypt(c) }   # 数字逐位加密，存成字符串数组
  end
end
```

* `@value` 的每一项是 **1 位十进制数字的 AES-128-ECB 密文**（存成 16 进制字符串）。
  密钥写死在游戏里：**`admin_alskmcndfj`**（旧文档写的 `admin_1941344749` 是照脚本里作者 QQ 号猜的，游戏解不开；V2.201 实际值见 `script00:1843`）（PKCS#7 填充，密文 16 字节 = 32 个 hex 字符）。
  `src/aes.py` 是纯 Python 实现（不依赖 pycryptodome），
  `encrypt_digit('7')` / `decrypt_digit(hex)` 单字符对单字符。
* 整数 = 各位数字解密后拼起来（`["a3..","9f.."]` → `"79"` → `79`）。
* `@code` 是游戏自己写的：
  `proc{|i| $game_party.item_number(i) + $game_party.item_number(i, $game_party.warehouse)}.call(物品id)`
  所以“校验值”其实是**累计获得数**。
* 游戏只给 `RPG::Item` 记账（脚本里直接 `return` 掉了 Weapon/Armor），
  而背包里三种对象是混装的 ⇒ 算总数时要**按 `@id` 分类过滤**。
* 改背包后必须重算：`GameEditor.sync_security_item(id)`；
  原本没条目的（游戏还没发过这件东西）就照上面的模板新建一个。

## 9. 周期检查：`$jiance` 与 `@cheated`

游戏每 300 帧（`Graphics.frame_count % 300 == 0`，约 5 秒）扫一次存档：

```ruby
if Graphics.frame_count % 300 == 0 and $game_system and !$game_system.cheated
  # 逐项比对：存银上限、仓库页号、角色等级/五维总点、召唤兽等级……
  # 不对就：$game_system.keyword << keyword
  #         $game_system.cheated ||= Graphics.frame_count
```

另外 `Change#inspect`（调试/内省）也会比对 `@code` 的期望值与实存值，
不一致同样置 `@cheated = Graphics.frame_count`。

`@cheated` 是个**帧计数定时炸弹**：

```ruby
if $game_system.cheated
  v = Graphics.frame_count - $game_system.cheated
  if v > 60*60*25-123        # = 89877 帧 ≈ 25 分钟（相对于记下时的帧数）
    msgbox "存档异常！#{...}"
    exit
```

`Graphics.frame_count` 每次启动都从 0 开始，所以一个 `@cheated = 134700` 的存档，
本次连续玩到第 224577 帧（约 62 分钟）就会弹「存档异常」退出；
而且只要 `@cheated` 非 false，上面的周期检查就**不再跑了**（`!$game_system.cheated`）。

⇒ 工具里「体检」会把它列出来，「清除作弊标记」把它置 `false`。
清零会重新武装周期检查，所以同时要把其他几项（存银/等级/五维/召唤兽等级）
都改回合法值。

## 10. Marshal 解析的坑（都踩过）

| 坑                                                   | 现象                                                                                  | 解法                                    |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------- |
| 非 ASCII 符号外面包了一层`I`                       | 写作`I :@体质 { :E => true }`；只认 `:`/`;` 会在中文实例变量名上报"坏符号 0x49" | `read_symbol()` 递归处理 `I` 前缀   |
| `c` / `m`（类 / 模块对象）**也占对象编号** | 不登记的话后面所有`@N` 链接整体错一位，最后报"链接越界"                             | 登记`ClassNode` / `ModuleNode`      |
| `I` 包装**不额外占**编号                     | 内层对象已经登记过，重复登记会错位                                                    | `I` 节点不 `register()`，只登记内层 |

另外还要支持：`}`（带默认值的 Hash）、`C`（String/Array/Hash 的子类）、
`u`/`U`（自定义序列化对象）、`l`（Bignum）、`f`（Float）。

排查手法：严格模式下（`marshal_ruby.STRICT_LINKS = True`）

* 校验 `@N` 链接不越界；
* 校验类名长得像 Ruby 类名；
* 校验实例变量名不是控制字符；
* `tools/re/parse_diag.py` 会把出错时的**递归调用链**（每层容器起始偏移）打出来，
  一眼看出是被哪一层套娃吃掉了。

## 11. 写回

* 改**标量**：只重编码那一个字段的 `[start, end)` 字节区间 —— 不影响任何 `@N` 链接。
* 改**容器/成员数**：`doc.mark_structural()` → `marshal_ruby.serialize_doc(objects)`
  **整档重写**（带符号表，17/17 与原明文逐字节相同），自动重新编号 `@N`。
  （旧接口 `patchwriter.serialize_tree` 会把链接展开成独立副本，现在不用了。）
* 写文件：先 `parse_stream(新明文)` 自检，能解析才加密覆盖，并自动留
  `*.bak.<时间戳>` 备份。

| `Armors`       | `RPG::Armor`       | 300  | ✅     |
| `Skills`       | `RPG::Skill`       | 320  | ✅     |
| `States`       | `RPG::State`       | 120  | ✅     |
| `Actors`       | `RPG::Actor`       | 300  | ✅     |
| `Classes`      | `RPG::Class`       | 300  | ✅     |

### 12.1 分段行与 `@note`（作者把不少信息塞这儿了）

两张表里都夹着**分段行**，作者用了**两种写法**：等号（`===药品===` /
`======剑=======` / `==【铠甲】==`）和破折号（`---剧情道具----` / `--坐骑--`）。
等号那批是作者给表分的段（Items 3 段、Weapons 20 段、Armors 16 段、Skills 13 段）；
破折号那批 Items 4 个、Actors / Classes 各 1 个（`--坐骑--`）、Skills 15 个
（`---特殊技能---` ＋ 14 个门派标题）。它们**都不是物品/技能** —— 界面上列出来
只会显示一个 `#1`，选中还会把那个 id 写进背包。`datatables.section_of()`
**两种写法都认**，`item_group()` / `skill_sections()` 把段名当「归属」。

⚠ **门派标题（`---五庄观---`）不算分段**，它只**结束**当前分段：门派技能的归属
交给 `tables/sect.py`（作者写的是简称 —— `---化生---` 对不上表里的「化生寺」）。
2026-10-06 修的就是这个：`_SEC_RE` 原来只认 `=`，`==特技==`（id 166）的段一路
吃到下一个 `=` 段（id 312「辅助技能」），把中间 13 个门派的技能归属全写成
「特技」。`---特殊技能---` 不在 `SECTS` 里，**算分段**（48 个召唤兽特殊技能）。

⚠ 「归属」的优先级是**分段 > 门派**：门派技能里 `index 10` 的「上古××」秘技
（601~612）两头都占 —— 既在 `$sects[id][:skills]` 里，也在 Skills 表的
「上古技能」分段里。按分段算才能保证「按某个分段筛出来的行，归属列全是那一段」
（`SkillManager.own_text` / `own_ok`，2026-10-04 补齐门派表后才撞上这个撞车）。

比分段行更常见的是**没名字的行**（画迹2 三张表一共 689 个），同样只显示 `#id`。
`item_map()` 把这两类一起滤掉。

技能的附加信息几乎全在 `@note` 里，游戏自己的解析器是 `ReadNote.read`
（逐行 `^\s*key\s*=`，等号右边按 Ruby 字面量解）：

| 键 / 标记 | 作用 | 谁在显示 |
| --------- | ---- | -------- |
| `state_details` | 状态 id 列表，配 `@description` 里的 `<S:N>` 占位符 | `<S:N>` 解成状态名 |
| `t_nums` / `t_times` | 目标数 / 攻击次数（`[值, 上限]`） | `description_ex(:目标数…)` |
| `t_dmge` / `t_rvhp` / `t_rvmp` | 伤害 / 气血恢复量 / 法力恢复量 | 同上 |
| `[mmp_cost]` | 消耗写成“全部魔法” | 技能浮窗 |
| `tp_cost` / `cooling` | 怒气消耗 / 剩余冷却 | 同上 |
| `lv` | 药品等级、内丹技能等级 | 物品浮窗、技能面板 |
| `price` | 覆盖 `@price`（`RPG::Item#price`） | 商店 |
| `[use_for_actor]` / `[use_for_baby]` | 只能角色用 / 只能召唤兽用 | `Window_Item#use_item` |
| `[Preposition]` | 要先选中它再点另一个格子（前置道具） | `Window_Item#use_item` |
| `[single]` / `[superposition]` | 不可叠加 / 可叠加（数据不同也不并格） | `usable_item.single?` |
| `[extend]` | 武器/防具带附加属性 | 装备浮窗 |

本仓库按这个口径把附加行接到说明后面（`skill_extra()` / `item_extra()`），
**只写核过语义的** —— 拿不准的（`t`、`etype_id`、`max`…）一律不写，
免得编出一条看着像真的的信息。
