# 待解决问题（v0.1 → v0.2 的工作清单）

## P0 —— 必须解决：拿到游戏写文件时用的那份"密钥状态"

### 现象

用 `main.dll` 自己的接口：

| 操作 | 结果 |
|---|---|
| `encryption_file` 加密任意文件 | ✅ 成功，输出 = 输入 + 8 字节 |
| `decryption_file` 解密"自己刚加密的文件" | ✅ 逐字节还原 |
| `decryption_file` 解密**游戏原来的** `save.rvdata2` / `Data\*.rvdata2` | ❌ 返回 1，但输出 **0 字节** |

说明：`main.dll` 里这份分组密码的**出厂状态**和**游戏进程内写文件时的状态**
不同。密文本身结构完全对得上（长度 = 明文 + 8，8 字节分组，ECB），
所以只差"密钥状态"这一个未知量。

### 已排除的假设

1. **第三参数不是口令**：任取 ""、"0"、"1"、"qqeat"、`Config.ini` 的 md5、
   各种中文词、文件名、路径、整数……（共 400+ 组合）都无法解密原档；
   而任意取值都能自洽往返（`probes/probe_20_brute3rd.py`、`probe_21_key2.py`）。
2. **不是 `init_key`**：`init_key(x)` 在 26 次循环里对 `(arg, i, i+1)` 做事
   （`i = 1..26`），且**任何** arg 都返回 0；从代码形态看它更像
   "初始化 26 个字母的按键表"（配合同库的 `call_input`），而不是密钥。
3. **不是缺 `init()`**：`init()` 的实现只做注册表
   `HKCU\SOFTWARE\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers\`
   的兼容性层设置（经典 RUNASADMIN/WIN7RTM 技巧），与密钥无关。
4. **不是环境问题**：在游戏根目录下、在沙箱副本里、加不加 `SetDllDirectory`
   都一样。
5. **不是标准算法**：解壳镜像里搜不到 TEA/RC5/Blowfish/AES/DES 的任何常量，
   也没有 CRC32 表（zlib 自带的除外）——是**自定义**分组密码。

### 下一步怎么做（按性价比排序）

1. **在游戏进程内取一次明文（最省事，能立刻做出可用版本）**
   * 游戏启动时 RGSS 会加载 `Data\main.rvdata2`（**明文**）里的那一句
     `Win32API.new('System/main','qqeat','v','v').call`。
   * 因此可以：备份 `Data\main.rvdata2` → 在里面追加一段 Ruby
     （`qqeat` 之后密钥状态已经装好），把我们想看的文件过一遍
     `System/main` 的 `decryption_file`，另存到别处 → 启动游戏 → 收集结果
     → 还原 `Data\main.rvdata2`。
   * 风险：`Config.ini` 里有 `md5=`、`System\Game.md5` 也有校验，改动
     `main.rvdata2` 可能触发保护（有 HTTP 上报接口）。**必须先整套备份，
     并考虑断网**。这条路线只用于**一次性勘察**，不适合做成品功能。
2. **把密钥状态逆出来（最干净）**
   * 解壳内存镜像已经在手（`probes/probe_04/05`，`probes/_dump_main.bin`）。
     下一步是找到 `encryption_buff` 真正的算法主体
     （impl `0x0FBAF` → 中间层 → 核心），把 8 字节分组的轮函数读出来。
   * 关键突破口：`qqeat`（impl `0x146B1`）一开头就从 `0x100BA3C9`
     拷贝了 8 个字节（实测是 `01 00 00 00 00 00 00 00`，像计数器），
     随后打开 `System/Game.md5`。密钥很可能在 `qqeat` 的前几十条指令里
     被构造出来 —— 建议从那里顺着 `mov ebx, <目标>; call 0x19Bxx`
     这套"间接调用蹦床"往下跟。
   * 有了算法就能用纯 Python 复刻，彻底摆脱 DLL。

3. **换一种思路：只用 ECB 的性质**
   * 若能从任意一份"明文 + 密文"对里拿到 $E$ 的足够多输入输出，
     还是不能推出密钥；但**如果能拿到游戏自己写的明文**（路线 1），
     就可以直接比对、定位要改的字段，然后**用同一份明文-密文对照**
     走"已知明文替换"——只要替换后的明文块与原来完全一致，密文不需要重算。
   * 这只能做"数值等宽替换"，做不了插入/删除。作为 v0.1.5 的临时方案可行。

## P1 —— 明文结构确认

拿到明文后要确认（v0.1 的 `xj_marshal` 已能解析多对象拼接流，但结构未核对）：

* 顶层到底是几个 Marshal 对象、分别对应 `$game_*` 的哪些；
* "机器码 / 存档主人"检查在哪（huaji1 有 `$存档id`，本作待查）；
* 金钱等敏感数值是否也有锁值结构（huaji1 用的是 `LockNumber`）；
* 等级 ↔ 经验的公式（huaji1 在 `Game_Actor#make_exp_list`）。

## P2 —— 工程收尾

* `tools/build.py`：PyInstaller 一键打包（参考 huaji1）。
* 打包时把 `XJCodec32.exe` 一起带上（**不要**带 `main.dll`：它有版权，
  而且有联网上报行为；让用户从自己游戏目录里加载）。
* 写回时做"写完再读回校验"（huaji1 的做法：加密→重新解密→逐字节比对）。
