# 逆向过程（v0.2：保护机制是怎么破的）

按时间顺序记下走过的路，包括失败的方向，免得下次重走。

## 0. 起点

v0.1 的结果是：工具骨架有了，但**游戏自己的文件一个都解不开** ——
直接调 `decryption_file` 只吐 0 字节。当时的结论（是错的）是
"main.dll 有出厂密钥状态，必须先知道游戏进程里的状态"。

## 1. 确认引擎与保护

* `Game.ini` → `Library=System\RGSS301.dll`、`Scripts=Data\main.rvdata2`，RPG Maker VX Ace。
* `System\main.dll`（382,976 字节）是 **MPRESS 加壳**的 32 位 DLL，导出
  `encryption_file` / `decryption_file` / `init_key` / `qqeat` / `shield` /
  `get_hard_disk_character` / `http_upload` … —— 典型国产"防作弊"壳。
* `Config.ini` 里 `md5=a36839d8…` 正好是 **Game.exe 的 md5**；
  解开 `System\Game.md5` 后看到清单里只有 `Game.exe` 和 `main.dll` 两个哈希
  —— **也就是说改存档 / 改 Data 不会被这个哈希校验发现**。
* `Game.exe` 和 `RGSS301.dll` 里都搜不到 `main.dll` / `decryption_file` 字样，
  说明 main.dll 是 **Ruby 运行时用 `Win32API.new` 加载**的。

## 2. 三个参数都是 UTF-8（踩过的坑）

反汇编里看到 `MultiByteToWideChar(0xfde9, …)`（CP_UTF8）和 `0x3a8`（936/GBK）。
实测传 ANSI 时中文路径会静默打不开文件 —— 必须传 UTF-8。

## 3. 静态搬"密钥状态"——失败

思路：把游戏进程里 main.dll 的内存镜像和我们自己加载的镜像做 diff，
把差异字节写回去（`tools/make_state.py` + 宿主里的 state 机制）。

结果：7973 个差异段 / 41853 字节（3.16%），其中只有 17 段是"A 为 0、B 非 0"；
逐个写回去**密文输出完全没变**。⇒ 密钥不是静态全局变量，这条路是死的。
（后来知道真相很朴素：**密钥就是调用时传进去的字符串**，根本不需要什么状态。）

## 4. 决定性实验：第三个参数就是密钥

同一段明文：用 `''` 加密再用 `'1'` 解密 → 0 字节；`'abc'` 加密 `'abd'` 解密 → 0 字节；
只有一致才还原。⇒ 第三个参数就是密钥本体（`tools/test_keyarg.py`）。

## 5. 爆破出 `761205` 与 `imoutogadaisuki`

给 32 位宿主加了 `brute` 模式：一个进程内 `LoadLibrary` 一次，
对候选列表逐个调 `decryption_file(目标, 临时文件, 候选)`，输出非空即命中。

候选来源：main.dll 解壳镜像 / Game.exe / main.dll 原文 / 配置里的 ASCII 串、
UTF-16 串、中文词、数字串，再加手工补充的 md5、标题、路径等。

* 拿 `Data\System.rvdata2` 当靶子 → 第 10259 个候选命中 **`761205`**；
* 对 `Data\Scripts.rvdata2` 用"`761205` 附近常量区（RVA 0x118850）+ 长度 3..12 子串 + 变形"
  当候选 → 命中 **`imoutogadaisuki`**。

途中发现 main.dll 在**某些候选密钥上会把宿主进程直接搞崩**（0xC0000005），
于是写了"分批 + 崩了跳过该候选"的驱动器 `tools/run_brute.py`，
并多进程并行（单次调用约 15 ms，6 路并行）。

## 6. 最后一个密钥：读游戏自己的脚本

`Data\Scripts.rvdata2` 一解开，游戏全部 Ruby 源码就到手了（被混淆过，但结构还在）。
直接搜到：

```ruby
SAVE_FILE_NAME     = 'save.rvdata2'
SAVE_FILE_PASSWORD = 'tiyan_version'      # ← 存档密钥
SAVE_FILE_AUTO     = "AutoSave/save%02d.rvdata2"
ok = ENCRYPTION_FILE.call(name, name, Config::File::SAVE_FILE_PASSWORD)
```

→ 存档密钥 **`tiyan_version`**。三个密钥全部到手。

> 顺带读到：`make_save_header` / `make_save_contents`（存档结构）、
> `Lock` 类（防作弊校验）、关键字检测（检测到作弊关键字会上报）。

## 7. 让解析器真的能读懂存档

拿到明文后解析仍然失败，一步步修（详见 `docs/存档格式.md` 第 5 节）：

1. `}`（带默认值的 Hash）不支持 → 报"未知类型 0x7D"；
2. `c`（Class 对象）不支持 → 报"未知类型 'c'"；而且 `c`/`m` **要占对象编号**；
3. 非 ASCII 符号被包成 `I :符号 {…}` → 报"坏符号 0x49"
   （本作实例变量名全是中文：`@体质`、`@法力`…，必踩）；
4. `I` 包装**不能**额外登记对象编号（内层已经登记过）。

修完之后：17 个明文文件（含 3 个存档、560 KB 的 Classes）全部完整解析，
解析终点与文件末尾逐字节对齐，重写自洽。

排查过程留下的工具：`tools/parse_diag.py`（打印出错时的递归容器链）、
`tools/hexdump.py`、`tools/check_db_parse.py`、`tools/verify_all.py`、
`tools/grep_ctx.py`（混淆脚本是超长行，按字符取上下文窗口最稳）。

## 8. 防作弊：不是加密，是校验和

真相在 `Lock` 类里：改数值本身不拦，但游戏**读**的时候会校验
`@value * 91 + 45 + floor(seed/800) == @master`，不相等就 `msgbox '游戏异常！'` 然后 `exit`。

所以修改器必须同步重算 `@master`（`xj_save.set_gold()` 自动做，
`xj_save.repair_locks()` 一次性修全档）。

## 9. 遗留 / 未做

* 游戏还有网络上报（`http_upload`）、关键字检测、`screen_capture` 等反调试手段，
  但**只改存档**不会触发；游戏内动态改内存（如 CE 类工具）才会。
* main.dll 用的分组密码没有还原成纯 Python（DLL 在手，没必要）。
  已知：8 字节分组 ECB、密文长度是 8 的倍数、无 IV、无随机量。
